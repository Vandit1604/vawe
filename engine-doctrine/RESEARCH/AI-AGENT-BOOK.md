# AI Agents in Depth (Bojie Li), read against this repo

Source: https://github.com/bojieli/ai-agent-book, `book-en/chapter1.md` to `chapter10.md`, about 1.18MB
of English text. All ten chapters were read in full: 2 and 4 in the main thread, 9 and 10 by one
dedicated reader, 1/3/5/6/7/8 by another. Every claim below names its chapter.

## What the book is, in five lines

It is an engineering textbook for the harness AROUND a model, built on one formula, `Agent = LLM +
Context + Tools`, across ten chapters with 93 companion experiments.
Its strongest material is mechanical: KV cache economics, what belongs in a static prefix, tool
description design, tool discovery at scale, evaluation and failure attribution, and the failure
taxonomy of multi-agent systems.
It is written for a chat-shaped agent serving users, so its running examples are customer service,
research and coding agents, and it is at its weakest on anything creative or judged by eye.
It is NOT a book about determinism, rendering, or any system whose output must be byte-identical
across runs, and that absence is where most of its advice stops applying here.
It contradicts itself in one useful place (chapter 4 recommends an embedding index for tool
discovery; chapter 5 reports that the two products which tried it have both abandoned it), and that
contradiction settles a live question here.

## ADOPT

Ranked by value. Each finding states the book's claim and chapter, the file it lands on, the change,
and how we would know it worked.

### 1. The census numbers in CLAUDE.md are a derivative maintained by hand, and three of three checkable figures are already wrong

**Book.** Ch3 gives the architecture: treat a knowledge base as three layers, a raw-evidence layer
that is append-only, a knowledge layer under review, and a serving layer, where "the index is
therefore a reproducible derivative, while the reviewed knowledge in Git is the source of truth."
Ch2 gives the risk, from the Agent Status Bar section: "models trust the status bar almost
unconditionally: write '3 calls made,' and the model accepts three without recalculating", followed by
the rule "maintain the status bar with code whenever possible." Ch5 gives the cost: "Outdated
documentation is worse than no documentation because it misleads future developers."

**Here.** This repo already has ch3's three layers and did not need the book to build them:
`engine-doctrine/MISTAKES.md` is the append-only evidence layer, `CLAUDE.md` plus `engine-doctrine/CRAFT/` is the knowledge
layer, and `engine-doctrine/EFFECTS.md` plus `make arsenal` plus the site is the serving layer. The serving layer
is correctly regenerated (`make regen`). The problem is that `CLAUDE.md` carries derivative FIGURES
inside the knowledge layer, typed by hand:

| CLAUDE.md says | live value | source of truth |
|---|---|---|
| line 410: "566 effects across 36 families" | **630 effects across 47 families** | `engine-doctrine/EFFECTS.md:990`, generated by `make regen` |
| line 408: "all 337 named things" | **445 named things** | `node harness/author/arsenal.mjs --census` |
| line 147 and five other lines: "134 gate-visible scenes" | **148** in the main tree | `node quality/gates/waiver-drift.mjs` |

The file already knows this is its failure mode. It admits having cited 93, 130 and 144 as the size of
one library in three sentences, and it warns the reader to "re-derive any number you intend to QUOTE".
That warning is the wrong shape of fix: it asks every future reader to distrust the file.

**Change.** The mechanism exists twice already. `quality/gates/docs-drift.mjs` checks every registry
COUNT quoted in `ROADMAP.md` and `PRIMITIVES.md` against the registry; `quality/gates/site-counts.mjs`
does the same for the site, and its header records nine wrong shipped figures as the reason it was
built. Neither reads `CLAUDE.md`, the file with the widest blast radius of the three. Add it as a
third target, or better, wrap the census figures in a generated block so the count has one owner.

**Observable.** Three known-wrong figures today. The gate is right if it names those three on the
first run and zero on the second. Long term: the number of hand-typed library figures in `CLAUDE.md`
that no gate reads, which should go to zero.

### 2. Nothing measures the prompt, and it is the only major component here that nothing measures

**Book (ch7, "Ablation Infrastructure" and "Prompt Sensitivity Assessment").** Ch7's opening premise
is "you can't improve what you don't measure", and its sharpest structural claim is that the object of
evaluation is the model AND the harness together: fix the harness and swap the model to find a model
limit; disable one harness component to find which part inside the harness matters. Its two
prescriptions are blunt. "**Every major feature should be independently disableable, and the team
should regularly verify the actual contribution of each feature**", because regular ablation runs
uncover **feature debt**. And: "**Every prompt change should run regression tests on the evaluation
set, just as code changes require CI.**" Ch1 supplies the number that makes this worth doing:
LangChain went from 52.8% to 66.5% on Terminal Bench 2.0, from outside the top 30 to the top 5, by
changing only the harness.

**Here.** There are roughly 70 gates in `quality/gates/` over the ENGINE, plus `snap-scenes` and
`probe-purity` proving byte-identical frames, plus `gate-mutation.mjs` at 95KB checking the gates
themselves. The 53,735-byte file that drives every authoring decision has no measurement of any kind.
Nobody can say which of its 28 sections changes an output, which means nobody can say what it costs to
move one, which is exactly why finding 3 below has been unsafe to act on until now.

**Change.** Not an ablation harness. One recorded experiment, once: take two locked briefs, author
each twice, once with the full `CLAUDE.md` and once with one section removed, and record what changed
in the resulting scene JSON. Ch7's own methodology note applies and is the part most likely to be
skipped: distinguish the mechanism metric from the target metric ("if you are testing 'shortening the
Agent's plan file length,' plan length is a mechanism metric"). Resident bytes is a mechanism metric.
The target is whether the film still obeys the rule.

**Observable.** The experiment IS the observable, and it is cheap: two briefs, four runs. Ch7's
warning about what it proves also applies, and this repo has learned it the hard way: "evidence from
one round should authorize only the next action that its scope can support."

### 3. About 22% of the always-loaded prompt is engine-maintenance doctrine that the primary task never touches

**Book (ch2, "Dynamic Prompts and Agent Skills"; ch9, "Sleep Learning" consolidation actions).**
Ch2 gives two costs for putting everything in one prompt: "wasted tokens" and "diluted attention",
the second being the one that matters, and names the resulting condition **context rot**: "overflow
means 'cannot fit any more,' while rot means 'it fits but cannot be found.'" Ch2's ablation is the
hard number: keeping all the rule CONTENT but removing hierarchy and ordering dropped Tau-Bench
success by over 30%. Ch9's consolidation list says it directly: "move local rules from the global
Prompt into domain Skills." Ch3 gives the loading shape, L0/L1/L2 with a per-directory `.abstract` and
`.overview`, and reports that "most queries can be resolved at L1."

**Here.** `CLAUDE.md` is 53,735 bytes over 28 top-level sections. Five of them are addressed to
somebody changing the ENGINE, not authoring a film, which the file's own opening forbids ("You do
**not** edit `scene.html` or the Go renderer unless explicitly asked"):

| section | bytes |
|---|---|
| ARCHITECTURE: fix it at the root, or fail there | 2,527 |
| SUGAR MUST NEVER SILENTLY NO-OP | 1,130 |
| LOOSE COUPLING: adding a thing must not mean touching everything | 1,710 |
| SPEED IS A PROPERTY YOU CAN LOSE WITHOUT NOTICING | 2,109 |
| The framework harvest | 4,339 |
| **total** | **11,815 (22%)** |

A second group is a resident copy of something that already exists behind a router. "NAME THE EFFECT
BEFORE YOU BUILD IT" is 3,274 bytes that ends by telling the reader to load the
`vawe-name-the-effect` skill, which holds the same procedure. That is a ch2 Layer-2 body sitting in
Layer 1. Same shape, smaller: "Hand-writing HTML? Beat the AI slop" (3,273) routes to `taste-skill`
and `impeccable`; "Reflecting a real website" (1,982) routes to `make sections`; "A DEMO IS A
TEN-SECOND FILM" (1,505) routes to `make demo`.

**Change.** Move the BODY of each to a doc or skill. `engine-doctrine/CRAFT/` already carries `when:`/`answers:`
frontmatter that `make doc-index` turns into a routing catalogue, which is ch2's Layer 1 with the
drift problem already solved. Keep the TRIGGER resident, one line each. Ch2's thought question 7 is
why the trigger must stay: "if the model does not know what it does not know, it cannot correctly
trigger the loading of a Skill." The harvest rule is the clearest case: its trigger ("after every
render, classify each problem framework-versus-authoring and log the framework ones") must stay
resident because nothing else fires it; its 50-line table does not.

**Two things this finding is NOT.** It is not a token-cost argument. Ch2's "Caching as an
Architectural Constraint" and ch5's note that project instruction files are "KV-Cache friendly because
they are a stable prefix" both mean a byte-stable `CLAUDE.md` is a cached prefix, so its cost is close
to a one-time cache write, not a per-turn charge. The argument is attention dilution only, and stating
the wrong reason is how a number in this repo gets quoted wrongly downstream. It is also not a licence
to COMPRESS: ch9 names **brevity erosion**, where "successive attempts at brevity can gradually erase
rare but important details, and interacting constraints can be collapsed into an overgeneral
principle." Move whole sections with their evidence intact. Do not shorten them in place.

**Observable.** Finding 2's experiment, run on the harvest section first because it is the largest and
the one whose loss would be most invisible: after the move, does a fresh session still log a
framework-class finding to `engine-doctrine/MISTAKES.md` when it hits one? If not, the trigger line was too thin.

### 4. The vision judge cannot say "I cannot tell from this sheet", and one of its seven dimensions rewards the judge's own bias

**Book (ch9 on rubrics, ch7 on LLM-as-a-Judge).** Ch9: "the judge should not merely assign a vague
overall score"; define the rubric in advance, score each item, cite the evidence, **and mark
uncertainty when the evidence is insufficient**. Ch7 adds the failure mode: **length bias**, "a
tendency to score longer, more detailed responses higher even when they are no more correct, much as a
human sitting an exam will pad out an answer they do not know", with the defence "regularly audit the
correlation between scores and response length." Ch7 also asks for weighted importance
(Essential / Important / Optional / Pitfall) with a veto, and for **self-contained** criteria:
"Abstract standards like 'the response demonstrates deep understanding' should be avoided."

**Here.** `quality/gates/rubric.mjs` gets most of this right already, which is why the two gaps are
worth naming. It defines seven dimensions in advance (lines 21-29), demands a per-frame located
finding (`beat N, <worst dimension>: <the issue> -> <the fix>`), and the A/B rubric is blind across
three independent judges with dimensions 4 and 5 dropped when no brand is named, specifically so a
campaign of fifteen films is not scored into sameness. That last decision is better than anything ch7
prescribes.

*Gap one: no abstention.* The verdict grammar at lines 47-49 has two values: "`PASS` only if every
frame clears every dimension. Otherwise `FIX`". A judge handed a still and asked about a dimension a
still cannot carry has no way to abstain, so it guesses, and the guess returns in the same shape as a
real finding. This repo solved this exact problem one directory over: `harness/author/arsenal.mjs`,
"AND IT MUST BE ABLE TO SAY IT DOES NOT KNOW ... the best of 420 things came back whether it answered
the question or not" (`engine-doctrine/MISTAKES.md` #552), fixed with a `CONFIDENT` threshold and a WEAK GUESS
heading. This is the repo's own "FIX THE RULE, NOT THE CALL SITE" applied to a consumer it was never
applied to.

*Gap two: dimension 6 is length bias written into the rubric.* "**Produced-not-generated**: crafted
density; not a word-on-empty-space slide." That instructs the judge to score density up, which is the
direction ch7 says a judge already leans by default. `CLAUDE.md` has an entire section arguing the
opposite case ("IS THE EMPTY PART OF THE FRAME DOING A JOB?", on active versus passive whitespace),
and it notes that no gate sees it. The rubric does see it, and scores against it.

**Change.** Add a third verdict, `CANNOT TELL`, plus what evidence would settle it ("this needs a
strip, not a still"). Rewrite dimension 6 so it asks whether the density is DOING something, which is
ch7's self-contained-criteria rule, rather than whether there is a lot of it.

**Observable.** For gap one: count judge findings that a look at the render does not confirm.
`engine-doctrine/MISTAKES.md` #155 is the archetype, a background "matched" on one still that was 2.5x too fast
in motion. For gap two, ch7 names the audit exactly: correlate judge score against layer count per
frame across the films already judged. If density predicts score independently of quality, dimension 6
is measuring the bias rather than the craft.

### 5. Discovery works. Triggering discovery is what fails, and ch4's real contribution is putting discovery on the critical path

This is the direct answer to live question 2 and is argued in full below. The change it recommends is
one line of output: `make dev` and `make check` should print, on every run, the handful of arsenal
entries that rank against this scene and appear nowhere in it. That is ch4's status-bar tool-name list
placed inside the loop the author is already in, rather than in `make preflight`, which is one
optional step at the start. Baselines already measured: beat blueprints used by 2 of 134 scenes, 12 of

### 6. A CLAUDE.md rule derived from one incident is a hypothesis, and 10 of the 12 it cites are single-incident

**Book (ch9, five-step knowledge distillation, and "A model treats observed behavior as the behavior
that ought to occur").** Ch9 refuses to formalize a lesson from one run: "reflection itself is not
evidence"; only content "consistent with environmental outcomes, supported across trajectories, and
showing positive transfer" becomes a formal document, and candidates must clear a **support
threshold**. Its worked failure is exact: on tau-squared-bench telecom, 19 of 20 derivation-set tasks
ended in escalation, so the model induced a rule making escalation mandatory. It wrote the failure
into the specification. Ch3 states the same rule for memory: "an arbitrary single operation must not
be treated directly as reliable experience."

**Here.** `engine-doctrine/MISTAKES.md` is the right artifact and needs no change: 565 append-only entries, each
naming what broke, the root cause, the fix and the gate, which is ch3's and ch9's immutable evidence
layer done well, including the retractions. The gap is the DISTILLATION step. Twelve `#NNN` entries
are cited in `CLAUDE.md`; only `#211` (three citations) and `#326` (two) rest on more than one
incident. The other ten generalize from a single trajectory to a standing instruction for every future
film.

The repo has already caught itself doing the tau-squared-bench error and named it correctly, which is
the best evidence the mechanism is live here: "Measured over the 134 gate-visible scenes: 56 carry
zero pictorial layers of any size ... **That was nobody's decision. It is debt, not a pattern to
copy.**" That sentence is precisely "observed behaviour is not the behaviour that ought to occur".

**Change.** Nothing structural. When a harvest promotes a mistake into a standing rule, mark the
support: `#505` alone is a hypothesis, `#214 + #216` is a pattern. Keep the existing habit of
labelling census-derived facts as debt rather than as house style.

**Observable.** Two counts, both cheap and both currently unknown. The 10-of-12 above is the first.
The second comes from ch7: every `engine-doctrine/MISTAKES.md` entry ends by naming the gate that now catches it,
so "how many of the 565 end in a runnable check, and how many end in 'the eyeball'?" is one grep, and
it is the coverage number for the whole memory.

### 7. The critic panel is six instances of one model, and the book says that is not six pieces of evidence

**Book (ch10, "Failure Mode Three: Homogeneous Convergence", and Table 10-1 on information gain; ch7
on Goodhart).** Two claims. Common-cause failure: "reviews generated by the same model in similar
contexts cannot automatically be treated as independent evidence", measured as 18 of 30 agents
independently choosing the same Git branch name. And the information-gain table: self-review by the
same model and debate over the same text yield NO new information and are "usually ineffective or even
harmful", while test execution, **rendered screenshots** and external tool verification yield new
information and improve results significantly. Ch7 adds the slow version of the same failure: with a
same-family judge, "the Agent will gradually learn to avoid the types of errors that the judging model
is not good at detecting, making the scoring system appear perfectly fine."

**Here.** `engine-doctrine/CRAFT/SUBAGENTS.md` justifies its roster entirely on lack of stake ("a self-grading
agent grades kindly"). By the book's table, five of six critics land in the strong row for a reason
the doc does not name: `beat`, `bg-motion`, `reveal`, `fidelity` and `seam` are each handed a RENDERED
ARTIFACT the author never saw. That is new information, and it is why the panel works. The sixth,
`copy`, is handed "the strings from the scene JSON, in beat order", the same text the author wrote.
That is the zero-gain row.

**Change.** Two sentences in `SUBAGENTS.md`: a critic's value comes from independent evidence, not
from freshness, and "what artifact does this critic see that the author did not?" is the admission
test for any new critic. Flag `copy` as the one that fails it.

**Observable.** Per-critic survival rate: of the findings each critic returns, how many does the main
thread's own look confirm? The book predicts `copy` is lowest. Worth having before changing the roster.

### 8. SUBAGENT-BUDGET.md is missing the number that reframes its own argument

**Book (ch10).** Anthropic's multi-agent research system "consumes about 15x the tokens of a normal
conversation, and **token usage alone explains about 80% of the performance difference**." Alongside
it, Tran and Kiela (2026): a single agent matched or beat five multi-agent architectures on multi-hop
reasoning at an equal thinking-token budget, unless context utilisation was degraded past a point.

**Here.** `engine-doctrine/CRAFT/SUBAGENT-BUDGET.md` records the 87-agent, 5,656,316-token run and argues from
COST. The 80% figure changes the argument's shape: the fan-out's gain may be mostly the spend, not the
topology, so the control that was never run is "one agent, same budget".

**Change.** One row in the doc's Rules list: before a fan-out, state what a single agent with the same
token budget would plausibly have produced. Rule 8 already says "prefer one agent for sequential
work"; this gives it a citation and a number instead of five blog posts.

**Observable.** One recorded control run. Honest note: that is a real cost and a single data point, so
this is the lowest-ranked ADOPT here.

### 9. Small, obviously right, left to you

Captured third-party HTML is untrusted content flowing into both a scene file and the agent's context.
`make capture` DOM-captures a live site and `mcp/server.mjs` `vawe_reflect` fetches an arbitrary URL.
`core/type/sanitize-html.js` refuses `transition` and `animation`, but for DETERMINISM, and nothing in its
header says which trust boundary it is or is not. Ch4's tool description poisoning, ch3's
"retrieved documents are the most typical vector for indirect prompt injection", and ch9's "LLM
summarization is a transformation for readability and processing, not a sanitization step that makes
the input harmless" all point at the same paragraph. The fix is a paragraph in that file's header
saying the sanitizer is a determinism filter and captured markup is untrusted data, never
instructions. No gate, no code.

## CONFIRMS

Places where an outside textbook argues independently for something this repo already built. Several
of these are the repo's most-contested decisions, and confirmation is the result.

<!-- doc-refs-allow: make slop · the target was RETIRED in 2026-08 (engine-doctrine/MISTAKES.md #326) and is named here only to record that it was deleted -->

**The verifier is the bottleneck, not the model.** Ch10, Loop Engineering: "the bottleneck of the loop
is the verifier, not the model ... with unreliable verification a faster loop only marks poor output
complete sooner." That is the argument behind `engine-doctrine/TASTE.md` and `CLAUDE.md`'s "a wrong gate is worse
than no gate because it manufactures confidence", and behind actually deleting `visual-vocabulary`
(squared a 590x18 rule into 590x590) and `make slop` (41 rules over a DOM dump carrying evidence for
three). Ch7 supplies the ordering rule the repo arrived at by pain: "**when Agent performance drops,
check the evaluation system first, then the Agent**", listing verifier bugs and drifting test cases as
things that "look identical to model degradation" in the headline number. The contrast-gate episode in
`SUBAGENT-BUDGET.md` (33 reported failures; the first one examined was a button 0.067 seconds into a
fade) is that rule, learned locally.

**A gate that invents findings is the same defect as a gate that misses them.** Ch1 names it: **false
refusal**, and "Guardrail evaluation should therefore test not only whether prohibited requests are
blocked, but also whether clearly permitted requests can still be completed." Ch7 gives the paired
form in SWE-bench Verified: FAIL_TO_PASS proves the problem was solved, PASS_TO_PASS proves nothing
else broke, and "Check only the first and an Agent can slip through by deleting or rewriting the
assertions that stand in its way; check only the second and you have checked nothing at all."
`CLAUDE.md` states both halves without the names: "The only acceptable shapes are 'no scene changes'
and 'these N changed, FAIL to PASS, here is why each was a false positive'. A single scene going PASS
to FAIL is a regression, not a discovery, until you have proven otherwise." Ch1 defines this pattern
canonically as **Boundary Set + Retention Set**; the two names are worth borrowing, the rule is
already right.

**No silent substitution, anywhere.** Ch4, "Fidelity of Parameter Passing": "there must be no
systematic discrepancy between the world the model perceives and the world the tool operates on", with
the Cursor case where the edit tool silently normalized curly quotes and the model could not diagnose
its own failure. Ch5 gives the principle in one line: "**Constraints over guidance**, the former means
'cannot be done,' the latter is merely 'advised against'." `core/registry/registry.js` is that principle
enforced structurally rather than by policy: `pick()` takes no fallback parameter, "so a silent
default is not expressible through this helper at all, and the fifth registry cannot be written
wrong." `CLAUDE.md`'s "SUGAR MUST NEVER SILENTLY NO-OP" and `core/engine/boot.js` throwing on a surviving
`cameraMove` (#424) are the same rule at two more sites.

**"Produced an answer" is not "completed the task".** Ch1, on a missing context component: "the
typical failure is not an error exit but an answer that looks flawless." Ch5 names its everyday form:
"the most common way a Coding Agent slacks off is to skip this stage entirely, writing the code and
reporting 'task complete' without ever running the tests. Defining 'tests pass,' rather than 'code
written,' as the completion criterion." `make ship` is that criterion, and it is the one command in
this repo that says a film is done.

**Right actions, wrong report.** Ch7 measures the category most evaluations hide, because they assert
only on final state: of 704 published tau-squared-bench baseline runs with a communication
requirement, 240 failed, 162 failed the communication check, and **80, a third of all failures, had
correct environment state and a wrong report**. Its detection method is fact-anchor comparison, walk
the agent's statements against the tool return values and take the first divergence.
`engine-doctrine/CRAFT/SUBAGENT-BUDGET.md` reached the same place from a real incident: "WAIT ON THE EXPECTED
FILE EXISTING ON DISK, never on the harness's completion notification. An agent can report success and
have delivered nothing", and "re-run the gate yourself, in the main tree, after copying anything back
... Two of them did not match." The repo has the rule; ch7 supplies the frequency, which is high
enough to justify how blunt the rule is.

**Explicit "not found" beats a confident wrong answer.** Ch4, Hierarchical Matching and Fallback: when
candidates score below threshold "the system should return an explicit 'not found', prompting the
Agent to rephrase and retry". `harness/author/arsenal.mjs` has `CONFIDENT = 0.47` and prints
everything below it as a WEAK GUESS, added because `dollyZoom` was offered twice in one day for
capabilities the engine does not have (#552). `core/registry/registry.js` goes past the book: a failed pick
searches every OTHER registry and says where the name does live ("`popIn` is a gsap effect, not an
anim. Did you mean `fx: \"popIn\"`?"). Ch4 describes nothing like that cross-vocabulary hint.

**Verification layers by formalizability.** Ch9's three-layer trajectory verification puts outcome and
process on code and environmental ground truth and sends "only hard-to-formalize aspects" to an LLM.
Ch7 states the corollary: "Every check that can be written as a programmatic assertion should stay an
assertion." `make ship` is that ladder: `author-check` and `audit` are code, `seam-check` pulls real
frames out of the mp4, and `make judge` is the only LLM step and is reserved for what the static gates
"cannot SEE".

**Knowledge as a codebase, with the index as a derivative.** Ch3's most transferable section says to
treat every knowledge change like a pull request over three layers, raw evidence append-only, a
reviewed knowledge layer in Git, and a serving layer where "the index is therefore a reproducible
derivative". That is `engine-doctrine/MISTAKES.md` / `engine-doctrine/CRAFT/` + `CLAUDE.md` / `engine-doctrine/EFFECTS.md` +
`make arsenal`, built here without the book. Ch3's periodic-reorganization rules land too: "Rewriting
only from existing summaries lets early omissions and misreadings propagate from one generation to the
next" is why commit `aa1aad2` removed two duplicates "found by scanning not reading", and "if evidence
insufficient, preserve the conflict and mark it" is what `CLAUDE.md` does with the unverifiable 10.3%
area figure instead of deleting or repeating it.

**Cross-linked docs, enforced.** Ch3: "Organize the knowledge base like Wikipedia: whenever an entry
mentions another, it links to that entry", with the warning that "many models do not do this
proactively, simply appending files in isolation. Therefore, the knowledge-writing prompt must
explicitly require this." This repo goes one better than a prompt: `quality/gates/doc-refs.mjs` and
`doc-map.mjs` check the links, and every doc's `when:`/`answers:` frontmatter generates the router.

**Hand the critic the artifact, not your description of it.** `SUBAGENTS.md` rule 1: "The moment you
write 'the sheet shows a clean grid' you have replaced its eye with yours." Ch10's Table 10-1 gives
the mechanical reason the doc does not: describing it converts a rendered-screenshot critic into
same-text debate. Ch4's Sidecar gives a second reason: it reads only structured fields precisely so
persuasive prose cannot reach it.

**The wrong modification layer.** Ch9 names the anti-pattern: "add one sentence to the Prompt telling
the Agent not to repeat the call" when the constraint is deterministically enforceable and belongs in
code. That is `CLAUDE.md`'s "ARCHITECTURE: fix it at the root, or fail there. A gate is the last
resort", and its corollary "a per-call-site opt-out is not a root fix". The book adds a clean test
worth quoting: if a constraint can be enforced deterministically, it never belongs in the prompt.

**Constrain actions, not only outcomes.** Ch5: "Deleting and rebuilding the database to 'fix' a
database fault does repair it, but the data is gone; deleting all the code to fix a compilation error
does make compilation pass, but the implementation is gone", called "the everyday form of reward
hacking in Agent tasks". Ch9 calls the same thing outcome-correct / process-wrong. `CLAUDE.md`'s
"FINISH THE FIX. Reverting is not a resolution" is the repo's version, and `gate-mutation.mjs` is the
machinery.

**Worktree per agent.** Ch10's failure mode one splits concurrency conflicts into simple (same file)
and semantic (cross-file logical contradiction) and prescribes working-copy isolation. That is how
fan-outs run here, and `SUBAGENT-BUDGET.md` records the trap the book does not mention: films are
gitignored, so a worktree fan-out over scenes merges cleanly and brings back nothing (#377).

**One agent for sequential work.** `SUBAGENT-BUDGET.md` rule 8 cites five blog posts. Ch10 cites Tran
and Kiela (2026) measuring it at an equal token budget across five multi-agent architectures.

## REJECT

**An embedding index with semantic pre-filtering over the arsenal.** Ch4's mid-tier answer to tool
explosion is "an embedding index built offline and updated incrementally", citing MCP-Zero's roughly
98% token reduction over about 2,800 tools and Anthropic's 49% to 74% accuracy gain. **Ch5 contradicts
ch4 and sides with what this repo already does**, reporting it as settled fact: "Terminal-based Agents
like Claude Code deliberately **do not build embedding indices**, relying purely on agentic grep +
glob for on-the-fly retrieval, this avoids maintaining indices that become stale as the code evolves,
eliminates the entire indexing infrastructure. IDE-based tools like Cursor initially took the opposite
approach ... **Today, IDEs like Cursor have also switched to on-the-fly grep + glob retrieval.**"
Our own reasons stand on their own: `arsenal.mjs` states as a design goal that it "OWNS NO LIST",
reading `kind`, `slot`, `names` and `blurbs` live from `defineRegistry` so "adding an effect to a
registry makes it searchable here with no edit", and our surface is 445 named things, not 2,800.

**The Agent Status Bar as an engine feature (ch2).** Everything in that section injects state into a
live agent loop. This engine renders video; it does not host the loop and cannot inject a message into
the harness driving it. The one place the pattern lands is finding 1, where `CLAUDE.md` IS the status
bar and the book's maintenance rule applies. Do not build a status-bar mechanism.

**Self-modifying harness (ch9: DeepSeek `dsh`, runtime plugins, `release_manifest.json`).** The
chapter's ceiling claim is that "the ceiling of self-evolution depends not on how well the model
writes code, but on how composable its host system is", with model-written plugins loaded at runtime.
`renderFrame(n)` is a pure function of `n`, and `snap-scenes` and `probe-purity` exist to prove
byte-identical frames across render order. A runtime-mutable engine negates that baseline directly.
The book's own safety rules point the same way: "the patch-generating Agent must not write to stable
code, validators, audit logs, or its own release gate." Our version is stricter and already shipped:
the engine does not change at runtime at all.

**Cross-family Proposer-Reviewer (ch3, ch4, ch7, ch10).** The book is specific and repeats it in four
chapters: proposer and reviewer should be "models of similar capability from different families",
because same-family models "share training data and preferences, and tend to fail in the same
scenarios". It is correct, it is the mechanism behind finding 7, and it is not buildable here: the
`Agent` tool exposes one vendor's family. The available partials are weak substitutes and should be
labelled as such rather than claimed as independence: varying the model TIER within the family, and
the thing that actually works, varying the EVIDENCE each critic sees. Ch7's fallback is the honest
one, "a single judge for daily use with periodic full multi-source audits", and even that audit needs
plumbing we do not have.

**Shared-forum multi-agent search (ch10).** Anthropic's 2026 result, 45 agents on a shared forum
finding 266 vulnerabilities with 27M tokens against 21 with 6.5M for independent parallel agents, is a
large real effect and contradicts `SUBAGENT-BUDGET.md` rule 5 on its face. It does not transfer. The
gain there comes from agents dividing and de-duplicating an unbounded search frontier. A six-critic
panel judging one rendered film has no frontier: each critic asks a different question about the same
fixed artifact, and a shared channel would only let them anchor on each other, which is ch10's own
cascading-amplification failure. Rule 5 stands as written.

**Debate and self-review patterns (ch10).** Listed because they are the most commonly copied
multi-agent patterns and the book rejects them by the criterion this repo already uses: no new
information, no gain. Worth adopting as one sentence and nothing more, ch10's decisive test: "Does the
collaboration provide information that a single Agent could not obtain while producing its answer?"

**Trajectory-prefix regression suites for agent behaviour (ch7).** Ch7 argues that for a production
agent needing reliability, "building the trajectory-prefix regression set often matters more than the
end-to-end one": freeze the context just before the first error and test only the next action, with an
acceptable action SET rather than one canonical action. It is a good idea and it is aimed at a
different system. Our regression suite asserts on ARTIFACTS (byte-identical frames, library-wide
PASS/FAIL diffs), which is the end-to-end form, and it is deterministic in a way an agent-behaviour
suite can never be. The transferable half is already in finding 6's second observable: ask which of
the 565 logged first-errors ended in a runnable check.

## The two live questions, answered

### Q1: CONTEXT. What belongs in the always-loaded prompt, and what should be fetched?

**The genre first, because it decides the criterion.** Ch5 classifies `CLAUDE.md` precisely: project
instruction files are "automatically injected into the context at the start of every session, acting
as project-level system prompts", and unlike a README they carry behaviour conventions and restricted
zones ("do not modify the `migrations/` directory"). So the test is not "is this true and useful", it
is "does this change behaviour on a task that starts today".

**Ch2's criterion is relevance frequency, and its cost is attention, not tokens.** Content that
applies to nearly every task stays. Content that applies to a subset moves behind a routing
description, because irrelevant resident content produces context rot: "it fits but cannot be found."

**Ch3 supplies the other half, and it is the part I would have got wrong.** Its analysis of why naive
retrieval fails names three obstacles, and the second is decisive here: **missing boundary semantics**.
"A statement of the form 'only ..., all others do not qualify' contains a universal boundary and a
negation that do not exist in any single ticket", and "a larger k cannot fix this". A universal
refusal is not recoverable by fetching, because no individual document contains it. That is the
principled rule for what stays resident:

> **Resident: universal boundaries, refusals, and triggers. Fetched: procedures, evidence, and
> anything scoped to one kind of task.**

**Applied to the 28 sections.**

*Stays, no argument.* The loop (`make dev` / `make check` / `make ship`), the brief contract, Hard
rules (no em dash, hook length), waivers versus legacy, and every section whose job is a refusal or a
trigger. These are exactly ch3's boundary statements. Ch2's tone advice supports the shouting-caps
style: "Uppercase words such as 'NEVER do X' increase instruction salience ... but overuse dilutes the
effect; reserve them for truly critical constraints." Twenty of 28 headings here are in caps, which is
past the point the chapter warns about, and worth one pass to decide which five need the volume.

*Moves, with the trigger left behind.* The five engine-maintenance sections in finding 3, 11,815
bytes, 22% of the file. None fires while writing a scene JSON, which the file calls the primary job.

*Moves, because it is a resident copy of something behind a router.* "NAME THE EFFECT BEFORE YOU BUILD
IT" (3,274 bytes, ends by naming the skill that holds the same procedure), "Hand-writing HTML? Beat
the AI slop" (3,273), "Reflecting a real website" (1,982), "A DEMO IS A TEN-SECOND FILM" (1,505). Keep
one line and the pointer.

*A structural point ch2 makes that this file half-obeys.* The ablation that dropped success by over
30% removed ORDERING, not content, and ch2 prescribes a process-driven SOP over a rule stack. This
file deliberately moved its ladder OUT ("THE PROCESS HAS ONE OWNER, AND IT IS NOT THIS FILE") because
three prose copies of one process went stale, and `make ship` now declares its own twenty steps when
it runs. By this repo's drift rules that was right, and it costs what ch2 would flag: an agent that
never runs `make ship` never sees an ordered process, only 28 independent rules. `make preflight` is
the mitigation and it is optional. Putting the ordered chain in nine lines at the top would close the
gap without re-creating the stale copy.

*A position note.* Ch2 measures position bias: "the model has higher recall accuracy for information
at the beginning and end of the context, while information in the middle is more likely to be
overlooked." "Hard rules" sits at line 198 of 745, near the worst position, and holds a constraint the
validator rejects the render for. The harvest rule is last, which is right.

**What NOT to do, and this is the half most likely to go wrong.** Do not shrink sections in place.
Ch9's brevity erosion is the named failure. Most of this file's length is EVIDENCE (the 46% figure and
its warning, the deleted gates, the seventeen-lines-above story), and the evidence is what makes a
rule survive being argued with. Move whole sections with their evidence. Do not sell any of it as a
token saving: a byte-stable `CLAUDE.md` is a cached prefix. And do not do it blind, which is why
finding 2 is ranked above finding 3: right now nothing here can tell you what removing a section
costs.

### Q2: DISCOVERY. Does ch4 suggest anything better than a searchable catalogue plus a completeness gate?

**Short answer: no, not for finding. Yes, for triggering, and triggering is our actual failure.**

Ch4 gives three tiers, "each more on-demand than the last": hierarchical organization with on-demand
loading; model-native proactive discovery (MCP-Zero, `tool_search`, `defer_loading`); and Skills,
"turning tool discovery into on-demand lookup", which it calls "the more modern, lower-maintenance
way" because "the 'embedding index + semantic matching' infrastructure disappears entirely".

Measured against that, our stack is already at the top tier and in two respects past it:

- `make arsenal Q="..."` is on-demand lookup over 445 named things with **nothing resident** and no
  index, ranked by token overlap against name, blurb and kind read live from `defineRegistry`.
- It can say it does not know (`CONFIDENT = 0.47`, WEAK GUESS), which is ch4's explicit-not-found
  fallback.
- `--kind` is ch4's two-level hierarchical match (its server-then-tool becomes our kind-then-name).
- `core/registry/registry.js` adds the cross-vocabulary hint, which ch4 does not describe anywhere.
- `quality/gates/arsenal-check.mjs` has no counterpart in the book at all. Ch4 assumes the catalogue
  and the capability set stay in sync; nothing in it addresses a capability the catalogue never
  mentions. On its 120 waivers against 173 exports: those are 120 documented answers to "is this
  export author-facing?", each with a reason, and the gate's header explains why an unexplained list
  would be worse. The book has no argument against that shape and I am not proposing to change it.

**So the catalogue plus the gate is right, and the census proves it is not the problem.**
`arsenal.mjs`'s own header carries the evidence: the `{type:"beat"}` blueprint mechanism (since
retired), which `CLAUDE.md` named as the number one defence against a slideshow, was used by 2 of 134
scenes; 12 of its
19 beats have never been used; `EXIT_FX`, eleven named exits, has zero users while every film needs
its layers to leave. The diagnosis is already written down: "That instruction has been given for
months and obeyed twice, so the problem is not persuasion."

An author who never searches is not helped by a better search. Ch2's thought question 7 names the
condition: "if the model does not know what it does not know, it cannot correctly trigger the loading
of a Skill."

**What ch4 offers that is genuinely better is architectural, not algorithmic: it puts discovery on the
critical path.** With `defer_loading: true` and `tool_search`, the schema is NOT in the prompt, so the
model cannot act without searching. Searching is not a virtue the agent has to remember; it is the
only route to the capability. Ch4 pairs that with a status-bar detail: "only a short list of tool names
maintained in the Agent's status bar."

Three ways to apply that here, cheapest first:

1. **Print the ranked unused arsenal on every `make dev` and `make check` run.** Ten lines: the
   entries that rank against this scene's own text and appear nowhere in it. That is ch4's status-bar
   name list, inside the loop the author is already in, on every iteration, with no new gate and no
   new file. This is the one to do.
2. **Make `make preflight`'s arsenal ranking an input the scene records**, so authoring transcribes a
   choice rather than recalling one. The receipt mechanism exists and already goes stale when the
   scene changes.
3. **Do not build proactive declare-match-inject.** Ch4 is blunt about its cost: "an embedding index
   to maintain offline, KV Cache invalidation to manage, dedicated training for weaker models." Ch5
   reports that the products which built it have since removed it.

**Observable.** The baselines are already measured and unusually clean: beat blueprints at 2 of 134
scenes, 12 of 19 beats at zero users, `EXIT_FX` at zero users. Re-run `make arsenal --census` after
ten new films. If those numbers have not moved, the change did not work, whatever it felt like.

## One closing warning the book aims squarely at us

Ch1: "The importance of the Harness does not mean that a more complex Harness is better", and its
named anti-pattern is the premature complex workflow, where "each new exception readily leads to
another node: the architecture grows increasingly complex while becoming less general." Manus's
slogan, quoted approvingly: "Less structure, more intelligence."

This repo has about 70 gates, a 28-section always-loaded prompt, eleven vendored skills and a
six-critic panel. By ch1's standard that is a lot of structure, and the honest reading is that the
book would ask whether each piece still earns its place. Two of our answers are already good: we
delete gates that measure the wrong thing and log the deletion, and we give each fact one owner. The
third answer, ch7's, we do not have: nothing here regularly verifies the contribution of each
component, so **feature debt is invisible by construction**. That is finding 2, and it is why it is
ranked where it is.
