# EDITING: wiring an editor to `formats/scene/schema.json`

## AGENT SUMMARY

- `.vscode/settings.json` maps every `formats/scene/*.json` (except `schema.json` itself) to
  `formats/scene/schema.json` via `json.schemas`, so VSCode knows which file is the contract for a scene.
- The convention: a scene may also declare `"$schema": "./schema.json"` itself. `sample.json` does
  this now, as the reference example.
- **Neither gives real field-level autocomplete today.** `formats/scene/schema.json` is not a JSON
  Schema document, so VSCode's JSON language server cannot read it. See "The gap" below before you
  build on top of either wiring.

## The wiring

`.vscode/settings.json`:

```json
{
  "json.schemas": [
    {
      "fileMatch": ["formats/scene/!(schema).json"],
      "url": "./formats/scene/schema.json"
    }
  ]
}
```

`!(schema).json` is an extglob: it matches every `.json` file in `formats/scene/` except
`schema.json`. `*.storyboard.md` files never match, because the pattern only matches `.json`.

If a `.vscode/settings.json` already exists when you read this, merge the `json.schemas` key into it.
Do not replace the file.

A scene may also carry its own pointer, so the file is self-describing even outside VSCode's
workspace settings (a teammate opening one file without the repo's `.vscode` folder, for instance):

```json
{
  "$schema": "./schema.json",
  "module": "scene",
  ...
}
```

`core/validate.mjs` only checks fields it knows about and ignores the rest (`module`, `audio`,
`theme`, and now `$schema` all pass through unexamined), so this key is safe to add: it does not
change what a scene validates against, or what the engine reads at render time. Verified: `make
validate D=formats/scene/sample.json` and `make site-counts` both stay green with `$schema` present.

## The gap: `schema.json` is not JSON Schema

This is the fact that decides everything else, so state it plainly. VSCode's `json.schemas` setting
expects the target file to be a real JSON Schema document (`draft-07` or `2020-12`): `type`,
`properties`, `items`, `required` as an array of names, `$ref`, and so on.

`formats/scene/schema.json` is a different, older, hand-rolled shape, generated by
`scripts/gates/schema-drift.mjs` from the `PROPS` declarations beside each layer's code
(`core/props.js`, `core/layers/vocabulary.js`). Its vocabulary:

| this file uses | JSON Schema uses |
|---|---|
| `fields` (object's child map) | `properties` |
| `item` (array's element schema) | `items` |
| `required: true` on the field itself | `required: [...]` as a sibling array on the parent object |
| `label`, `hint` | `title`, `description` |

None of these line up. Pointed at it as-is, VSCode's JSON language server sees an object with no
`type` and no `properties` it recognises, treats the schema as "anything goes", and shows no
autocomplete and no errors. The wiring above is real and will not break anything, but by itself it is
inert: it names the right file, in the right convention, for a dialect the file does not speak.

Adding a top-level `"$schema": "https://json-schema.org/draft/2020-12/schema"` declaration to
`schema.json` was considered and rejected. It would not just be unhelpful, it would be false: the file
would claim a dialect its keywords do not follow, which is worse than the current silence. `schema.json`
was left untouched.

## Follow-up for whoever owns `core/registry.js` / `schema-drift.mjs`

The fix is a second, generated file: a real JSON Schema translation of `formats/scene/schema.json`
(`fields` → `properties`, `item` → `items`, per-field `required: true` collected into the parent's
`required: [...]` array), emitted by `scripts/gates/schema-drift.mjs` alongside the existing output.
Point `.vscode/settings.json` at that file instead once it exists. That is a decision for the schema's
owner, not something this note builds, because a translated schema is a second copy of a fact
(`schema.json`'s own shape) that has already drifted once (the 566/638, 337/445, 134/148 counts
`AGENTS.md` warns about) and a second copy needs someone committed to keeping it in sync.

One thing worth carrying into that future file, borrowed from how another engine's Studio drives its own
schema editor (`ZodSwitch.tsx`): a `label`/`hint` value in a field already reads as a `.describe()`
brand string. A `format` or `x-widget` tag on top of that could later select a richer input (a colour
swatch for a hex field, a slider for a 0..1 range) instead of a bare text box. Not built now: it is a
widget system on top of a schema that does not exist yet.
